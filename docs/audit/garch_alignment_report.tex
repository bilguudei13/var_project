\section{Classification of \texttt{GARCH R.r}}\label{sec:classification}
% =============================================================================

\textbf{Role: Separate deliverable} --- a comprehensive per-factor GARCH
diagnostic study.

Evidence supporting this classification:
\begin{itemize}
  \item Operates on \code{data/processed/risk\_factors.csv} (six individual
    factors: SPY, DGS10, GLD, EURUSD, SPY\_level, VIX), not the portfolio
    P\&L used by \code{garch\_evt.py}.
  \item Pipeline: ADF stationarity $\to$ auto-ARIMA $\to$ ARCH test $\to$
    marginal distribution selection (nine candidate families) $\to$ GARCH
    fitting $\to$ six validation criteria (Ljung-Box, GoF, sign bias,
    Nyblom). No EVT, no VaR, no backtesting.
  \item Uses the \code{rugarch} package (R), while both Python files use the
    \code{arch} package.
  \item No shared output that \code{garch\_evt.py} is meant to replicate
    numerically.
\end{itemize}

\textbf{Scope overlap with \code{garch\_evt.py}:} Low. The R file establishes
that GARCH(1,1) with Student-$t$ innovations is appropriate for these financial
series, and \code{garch\_evt.py} inherits that choice. No point-by-point
numerical match is expected.

\textbf{Consequence for the audit:} \code{GARCH.py} is the sole authoritative
Python reference. \code{GARCH R.r} informs background methodology choices
(Student-$t$, sGARCH(1,1)) but its R-specific choices (ARMA mean
pre-filtering, \code{rugarch} solver, per-factor scope) do not propagate to
\code{garch\_evt.py}.

\section{Code Structure and Documentation Review}\label{sec:structure}
% =============================================================================

\subsection{Function decomposition}

\code{GARCH.py} has two functions: \code{plot\_stylised\_facts()} (EDA) and
\code{run\_garch\_pipeline()} (fit + print).  No residual extraction, no
forecast, no VaR.

\code{garch\_evt.py} is fully decomposed: \code{load\_data()} $\to$
\code{fit\_garch\_expanding()} $\to$ \code{plot\_garch\_diagnostics()} $\to$
\code{compute\_garch\_evt\_var()} $\to$ \code{backtest\_garch\_evt()} $\to$
\code{plot\_garch\_evt\_results()} $\to$ \code{save\_results()}.  More modular
than \code{GARCH.py}, appropriate given the additional scope.

\subsection{Parameter naming}

\code{GARCH.py} does not extract individual GARCH parameters explicitly
(only \code{res.summary()} is called). \code{garch\_evt.py} uses natural
names \code{mu}, \code{omega}, \code{alpha1\_d}, \code{beta\_d} that
mirror the \code{arch} library's \code{params['mu']}, \code{params['omega']},
etc. No conflict.

\subsection{Docstring and comment style}

\code{GARCH.py} uses plain triple-quoted strings. \code{garch\_evt.py} uses
extended NumPy-ish style with Parameters/Returns sections --- more thorough
and appropriate for its larger scope. No alignment change needed.

\subsection{Citations}

\code{GARCH.py} cites no references. \code{garch\_evt.py} cites Irle
(pp.\,172--186, 212--225) and McNeil \& Frey (2000). Both are appropriate
given \code{garch\_evt.py}'s GARCH+EVT scope.

\subsection{Error handling}

\code{GARCH.py} has no explicit convergence handling. \code{garch\_evt.py}
uses \code{warnings.catch\_warnings()} during GARCH fitting, and
\code{try/except} with \code{warnings.warn()} fallback for GPD fitting
(B5). \code{garch\_evt.py}'s error handling is more robust.

\subsection{Output file conventions}

\begin{itemize}
  \item \code{GARCH.py}: writes to \code{report/figures/} (line~18).
  \item \code{GARCH R.r}: writes to \code{outputs/figures/} and
    \code{outputs/tables/}.
  \item \code{garch\_evt.py}: writes to \code{outputs/figures/} and
    \code{outputs/tables/} --- \textbf{aligned with the R convention}.
\end{itemize}

The \code{GARCH.py} $\to$ \code{report/figures/} divergence is a pre-existing
inconsistency internal to \code{GARCH.py}; it does not affect
\code{garch\_evt.py}. (Follow-up item: update \code{GARCH.py} line~18 to
\code{outputs/figures/} for project consistency.)
